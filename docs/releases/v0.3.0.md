# Release notes: v0.3.0

24 changes, 5 requiring action.

## Upgrading to this release

Every release asks these of a workspace, whatever its entries say. Make them on a branch, in order, then read the
entries below.

**1. Move every `@sssb/*` package to 0.3.0, together.** In the root `package.json`, each
`apps/<app>/package.json` and `apps/<app>/infra/package.json`, and any package of your own that depends on one,
change each `@sssb/*` version, then install and commit the lockfile. First make any "Scaffold changes to apply by
hand" entry below that touches how packages install, or the install keeps the old release.

```json
{
    "@sssb/kit": "^0.3.0",
    "@sssb/tools": "^0.3.0",
    "@sssb/eslint-plugin": "^0.3.0",
    "@sssb/cdk": "^0.3.0"
}
```

```sh
pnpm install
```

**2. Refresh the app guide's copy,** the rules every agent in your repository follows. `sssb doctor` fails until the
copy is the installed kit's; read the diff of `.claude/sssb-guide.md`.

```sh
pnpm exec sssb guide
```

**3. Raise both pins to this release's commit.** The reusable workflow's `uses:` in
`.github/workflows/checks.yml` and the plugin marketplace's `ref` in `.claude/settings.json` are two pins on one commit
of SSSB's repository, and the installed `@sssb/kit` records it. This reads it there and writes both, printing each pin it
changed, and does nothing to one that is already current. It refuses, changing nothing, when the kit carries no release
stamp or a file is not the shape it edits:

```sh
pnpm exec sssb pin
```

If it refuses, make the two edits by hand: the `uses: safeinsights/sssb/.github/workflows/app-checks.yml@<commit>` line and the
marketplace's `ref`. The commit is the one `sssb doctor` names beside a pin that differs or, for a kit with no stamp, the one this prints: `git ls-remote https://github.com/safeinsights/sssb 'refs/tags/v0.3.0' 'refs/tags/v0.3.0^{}' | tail -n 1 | cut -f 1`. A pin takes the commit's SHA, never the tag `v0.3.0`, which can be moved.

Then each person updates their installed plugin and restarts Claude Code:

```sh
claude plugin marketplace update sssb
claude plugin update sssb@sssb --scope project
```

**4. Apply each entry below, then drop what it left unused.** Do each "To adopt" and delete what each "Now deletable"
describes, then run `pnpm knip`. A vendor SDK your app listed only for code you deleted (`@aws-sdk/client-s3` for a
copy of the kit's S3 storage adapter, say) is now flagged as unused, because the kit's adapter that replaces it
carries its own copy: remove it from the `package.json` that lists it, unless other code still imports it.

```sh
pnpm knip
```

**5. Check, then push.** Read every line `sssb doctor` reports, not just the last: it fails on versions out of step and
a stale guide copy, and only reports a pin that is not the release commit.

```sh
pnpm exec sssb doctor
pnpm verify
```

## Seam changes

### Job handlers get the auth port, and the digest addresses real members

Action: required · `@sssb/kit`

**What changed.** A job handler's context (`JobHandler`'s second argument, `@sssb/kit/ports/jobs`) now carries `auth`,
the auth port, for handlers that address people, and an optional `resolveLocale`, a person's own locale where the runner knows it (in a simulated world). The framework's `digest-email` handler uses it: it sends a team's
digest to the team's first active admin (else its first active member) as `auth.listMembers` lists them, which in a
deployment is the identity provider, instead of a person from the seed. In a deployment, a team with no active
member gets no digest; in a simulated world the digest now also reaches accepted invitees and writes in the recipient's current profile locale, and a team with no one to address still gets the synthetic `<org>@digest.example` address. No job handler reads the seed any more, and none may.

**To adopt.** Where your own code calls a job handler directly (a unit test, say), pass `auth` in its context beside
`llm`: an auth port, or a stand-in typed as one. A handler of yours that addresses people asks
`ctx.auth.listMembers(orgSlug)`, never `@sssb/app-config/seed`, which a deployment does not have.

**Now deletable.** A recipient list or address map a handler kept so that it would not read seed people in a
deployment.

### Real-mode sign-in: `withAuthProxy` runs Clerk's middleware around your proxy

Action: required · `@sssb/kit`

**What changed.** SSSB's Clerk auth adapter calls Clerk's `auth()`, which refuses any request Clerk's middleware did
not see, and SSSB never ran that middleware, so in real mode every sign-in failed. The new published subpath
`@sssb/kit/adapters/proxy` exports `withAuthProxy(proxy)`: in real mode it runs your proxy inside Clerk's
`clerkMiddleware`, loading it with `import()` on the first request; in simulated mode it runs your proxy as it is and
loads no Clerk code, so `pnpm dev` stays hermetic. It protects no route: each route's `authorize()` still does.

**To adopt.** In `src/proxy.ts`, wrap your proxy and send it every API route as well as your pages. Your proxy still
decides what each path gets; let an API route through untouched:

```ts
import createMiddleware from 'next-intl/middleware'
import { NextResponse } from 'next/server'
import { withAuthProxy } from '@sssb/kit/adapters/proxy'
import { routing } from '@sssb/kit/i18n/routing'

const locales = createMiddleware(routing)

export default withAuthProxy((request) =>
    request.nextUrl.pathname.startsWith('/api') ? NextResponse.next() : locales(request),
)

export const config = {
    matcher: ['/((?!api|_next|_vercel|.*\\..*).*)', '/api/:path*'],
}
```

A proxy that already runs on every path (`matcher: '/:path*'`) keeps its matcher. Clerk's middleware reads the keys the
auth adapter needs (`NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`). In a deployment, also set `CLERK_JWT_KEY`
to your Clerk instance's JWT public key (PEM, `\n` escapes accepted): Clerk does not read it itself, so the kit passes
it on, and Clerk then checks each session without a call to Clerk's API. A value that is not a 2048-bit RSA public key
stops the proxy at its first request. Clerk is never shown a request's `Authorization` header (users sign in by Clerk's
session cookie), and your proxy and routes still receive it.

**Now deletable.** A wrapper of your own that runs your proxy inside `clerkMiddleware` in real mode: an adapter that
imports `@clerk/nextjs/server` for the proxy, the run-mode check and `import()` in `src/proxy.ts` that load it, and a
test that mocks the run mode to reach it.

### An app with no extra subject fields no longer silences a lint rule

Action: optional · `@sssb/kit`

**What changed.** `AbilitySubject` in `@sssb/kit/core/abilities` is now an intersection, `AppSubjectFields & { type; orgId?; ownerId? }`, instead of an interface that extends `AppSubjectFields`. The seam's `AppSubjectFields` may therefore be an interface, a type alias or a mapped type. An app with no fields used to declare an empty interface and suppress `@typescript-eslint/no-empty-object-type`, the one place the "empty registration is the off switch" rule was not true; `apps/starter` now writes `export type AppSubjectFields = Record<never, never>`. An app that declares an interface keeps working unchanged, and so does every caller of `AbilitySubject`.

**To adopt.** Nothing breaks if you do nothing. If your `src/app-config/abilities.ts` carries an empty `interface AppSubjectFields {}` under an `eslint-disable-next-line @typescript-eslint/no-empty-object-type`, replace both with `export type AppSubjectFields = Record<never, never>`. Only code that wrote `interface X extends AbilitySubject` is affected, and it needs `type X = AbilitySubject & { … }` instead.

**Now deletable.** An `eslint-disable-next-line @typescript-eslint/no-empty-object-type` above an empty `AppSubjectFields` interface.

### The Simulator's People, Mail and Jobs tabs on an app's own `pnpm dev`

Action: optional · `@sssb/kit`

**What changed.** Two new published subpaths serve the Simulator panel from an app's own server. `@sssb/kit/server-lib/simulator-api` exports `simulatorApi(request, context)`, one handler for every `/api/simulator/*` call, simulated mode only (404 in a real build), with People (`summary`, `viewpoint`), Mail (`mail`, `mail/clear`, `mail/seen`) and Jobs with the world clock (`jobs`, `jobs/run-pending`, `schedules`, `clock`, `schedules/run-due`); any other path is a 404, every POST must send `content-type: application/json` (415 otherwise), a known path with the wrong method is 405, `viewpoint` answers only a path on this origin, and `mail/seen` only someone in the world. `@sssb/kit/components/simulator/simulator-host` exports `SimulatorHost`, the panel client that calls it. `SimulatorPanel` now shows a tab only when its host passes that tab's props (People always), so a host that wires every tab sees no change.

**To adopt.** Mount the handler with one route file, `src/app/api/simulator/[...path]/route.ts`, whose `GET` and `POST` each open with the simulated-mode 404 and import the handler only after it, so the authorization scan's `simulator/` exemption holds:

```ts
import { isSimulated } from '@sssb/kit/adapters/index'
import type { SimulatorRouteContext } from '@sssb/kit/server-lib/simulator-api'

export async function GET(request: Request, context: SimulatorRouteContext): Promise<Response> {
    if (!isSimulated) return new Response(null, { status: 404 })
    const { simulatorApi } = await import('@sssb/kit/server-lib/simulator-api')
    return simulatorApi(request, context)
}
// POST: the same body.
```

Then render the panel around the page from `src/app/[locale]/layout.tsx`, in simulated mode only and through a dynamic import, as SSSB's starter does: `const { SimulatorHost } = await import('@sssb/kit/components/simulator/simulator-host')`, then `<SimulatorHost locale={locale}>{children}</SimulatorHost>`. An app with Simulator glue of its own (route files under `src/app/api/simulator/` and a client glue) can keep it: a route file of its own still wins for its path. Snapshots, presets, tours, the other subsystem tabs, the dev ticker and app-registered tabs are not served yet; keep your glue while you use them.

**Now deletable.** Hand-written `src/app/api/simulator/{summary,viewpoint,mail,mail/clear,mail/seen,jobs,jobs/run-pending,schedules,clock,schedules/run-due}/route.ts` wrappers over the fake adapters, once a client glue no longer calls anything else under `/api/simulator/`.

## Operator actions

### `SssbApp` takes request bodies through CloudFront, and pins the server's `HOSTNAME`

Action: required · `@sssb/cdk`

**What changed.** A deployed app answered 403 to every `POST`, `PUT` and `PATCH`: its Function URL sits behind
CloudFront's origin access control, and Lambda refuses a request there whose body hash (`x-amz-content-sha256`) is
missing, which CloudFront never adds. `SssbApp` now runs a Lambda@Edge function on the default behavior's origin
request that sets that hash from the body, so request bodies up to 1 MB reach the server, and a larger one answers 413.
The server's environment also sets `HOSTNAME=0.0.0.0`, where Next's standalone server listens: with `127.0.0.1`,
requests through the auth provider's proxy fail. Lambda@Edge lives in us-east-1 only, so an environment-agnostic stack
now deploys to us-east-1 only (elsewhere CloudFront refuses the function and the deploy rolls back), and a stack with
an explicit region outside us-east-1 gets the function in a second stack in us-east-1, `edge-<region>-…`, carrying the
stack's tags.

**To adopt.** Upgrade and run `cdk diff`. It shows, for the stack: a new `BodyHash` function with its role and a
version, the distribution's default behavior gaining a `LambdaFunctionAssociations` entry (`origin-request`,
`IncludeBody`), and `HOSTNAME` added to the `Server` function's environment; no stateful resource changes. A stack with
an explicit region outside us-east-1 also gets a cross-region reader custom resource, and a new stack in us-east-1:
run `cdk bootstrap aws://<account>/us-east-1` first. `cdk deploy` with no stack name then refuses (the app has two
stacks): name your stack, which deploys the us-east-1 one first, or pass `--all`; `--exclusively` skips it. An
environment-agnostic stack deployed outside us-east-1 must take an explicit `env` before upgrading. A teardown can now
fail on the edge function while CloudFront drops its replicas (up to a few hours): delete the stack again then. Leave
`HOSTNAME` out of your deploy pipeline's `run.sh`.

**Now deletable.** A Lambda@Edge function of your own that sets `x-amz-content-sha256` on the distribution's default
behavior, with its role and the escape-hatch override (`LambdaFunctionAssociations`) that attaches it: keeping the
override replaces `SssbApp`'s association with yours. An `export HOSTNAME=0.0.0.0` in your `run.sh`.

### `SssbApp` sends HSTS and safe security headers

Action: required · `@sssb/cdk`

**What changed.** The three behaviors `SssbApp` builds (the app's pages, `/_next/static/*` and `/assets/*`) now carry
AWS's managed SecurityHeadersPolicy:

- `Strict-Transport-Security: max-age=31536000`;
- `X-Content-Type-Options: nosniff`;
- `Referrer-Policy: strict-origin-when-cross-origin`;
- `X-Frame-Options: SAMEORIGIN`;
- the legacy `X-XSS-Protection: 1; mode=block`.

Each yields to a header your app sends itself, except nosniff, which is always sent. A managed policy takes none of
your account's 20 custom response headers policies.

`hstsIncludeSubdomains: true` adds `includeSubDomains` to HSTS. It builds a custom policy with the same headers (one of
the 20). Pass `responseHeadersPolicy` to use a policy of your own on those behaviors instead; it replaces the whole
set. The policy in use is exposed as `responseHeadersPolicy`: give it to any behavior you add yourself, which gets
none otherwise.

**To adopt.** Upgrade and run `cdk diff`. It shows `ResponseHeadersPolicyId` set on the distribution's default
behavior and on `/_next/static/*` and `/assets/*`, and, with `hstsIncludeSubdomains: true`, a new `SecurityHeaders`
response headers policy. No stateful resource changes. Before deploying, check three things:

- **Framing.** If another site frames your app, send a CSP `frame-ancestors` naming it from the app, or pass a policy
  of your own. `SAMEORIGIN` refuses other sites' frames.
- **Content types.** Your deploy pipeline must upload the static files with their real `Content-Type`, since `nosniff`
  makes a browser refuse a script stored as anything else.
- **Your own policy.** If you already attach one by escape hatch (`ResponseHeadersPolicyId` overrides on the
  distribution), either pass it as `responseHeadersPolicy` and delete the overrides, or delete both and take SSSB's.
  If you keep the overrides, they replace SSSB's policy behavior by behavior.

**Now deletable.** A response headers policy of your own that adds only HSTS, nosniff, a referrer policy and frame
options, and the escape-hatch overrides that attach it.

### `SssbApp` tells the app the host the viewer asked for, and redirects plain HTTP everywhere

Action: optional · `@sssb/cdk`

**What changed.** CloudFront sends the server's Function URL its own `Host`, and forwarded a viewer's
`X-Forwarded-Host` as sent, so what reads that header in a deployed app (Clerk's request URL, Next's server-action origin
check, next-intl's domain redirects) saw the Function URL's host, or one the viewer chose. `SssbApp` now runs a
viewer-request CloudFront Function on the default behavior that sets `x-forwarded-host` from the `Host` CloudFront
received (lowercased, any port dropped) and `x-forwarded-port` to 443, overwriting what the viewer sent, and drops a
viewer's `Forwarded`. Next's own `request.url` names the server's own address (`localhost` and its port), not the viewer's host. It is exposed as `forwardedHost`: associate it with any behavior of your own
that reaches the server. The `/_next/static/*` and `/assets/*` behaviors now redirect HTTP to HTTPS, as the default
behavior already did.

**To adopt.** Upgrade and run `cdk diff`. It shows a new `ForwardedHost` CloudFront Function, the distribution's
default behavior gaining a `FunctionAssociations` entry (`viewer-request`), and `ViewerProtocolPolicy` on the two static
behaviors changing from `allow-all` to `redirect-to-https`. No stateful resource changes. If you added a behavior of
your own that reaches the server, associate `forwardedHost` with it on `viewer-request`.

**Now deletable.** A CloudFront Function of your own that sets `x-forwarded-host` from the viewer's `Host`, and the
escape-hatch override (`FunctionAssociations` on the default behavior) that attaches it: keeping the override replaces
`SssbApp`'s association with yours.

### Machine callers send their credential in its own header, which CloudFront passes through

Action: optional · `@sssb/kit`, `@sssb/tools`, `@sssb/cdk`

**What changed.** `withWebhookSecret` (`@sssb/kit/service-auth/webhook`) reads the shared secret from
`x-sssb-webhook-secret`, and `verifyServiceCaller` (`@sssb/kit/service-auth/verify`) reads a service token from
`x-sssb-service-token`, each exported as a constant (`WEBHOOK_SECRET_HEADER`, `SERVICE_TOKEN_HEADER`). The header wins
when present; `Authorization: Bearer …` is still accepted when it is absent. The reason: `SssbApp`'s CloudFront signs
every request it passes to the server's Function URL, and its signature replaces the `Authorization` header, so a
credential sent there through the public host never reached the route and every such call answered 401. `pnpm tick`
and `SssbApp`'s scheduled tick send the new header.

**To adopt.** Every caller of your webhook and service routes that goes through your deployment's public host (a
scheduler, a build's completion callback, a service) sends `x-sssb-webhook-secret: <secret>` or
`x-sssb-service-token: <jwt>` instead of `Authorization: Bearer …`. A caller that reaches the server another way may
keep `Authorization`, but the header works everywhere.

**Now deletable.** A workaround that delivered a webhook secret or service token around CloudFront because
`Authorization` never arrived.

### Real mode requires only the optional ports your app uses

Action: optional · `@sssb/kit`, `@sssb/cdk`

**What changed.** Each of SSSB's optional ports has a switch the server reads at boot: `LLM_PROVIDER` (`anthropic`
or `none`), `EMAIL_PROVIDER` (`mailgun` or `none`), `INBOUND_EMAIL_PROVIDER` (`mailgun` or `none`) and `JOBS_RUNNER`
(`codebuild`, `in-process` or `none`). A port switched to `none` is absent: real mode no longer requires its settings
(`ANTHROPIC_API_KEY`; `MAILGUN_DOMAIN`, `MAILGUN_API_KEY`, `EMAIL_FROM`; `MAILGUN_WEBHOOK_SIGNING_KEY`;
`JOBS_CODEBUILD_PROJECT`), never loads its SDK, and a call through it throws an error naming the switch. An unset
switch is its first value, so a deployment that sets none requires exactly what it did. `SssbApp` sets the switches
from a new, optional `params.ports` (`llm`, `email`, `inboundEmail`, `jobs`), and refuses a port or a value it does not
know. `required-env.json` now also lists what each choice requires.

**To adopt.** Add `ports` to `apps/<app>/config/params.ts`, beside `database`, with `none` for each port your app
does not use, e.g. `ports: { llm: 'none', email: 'none', inboundEmail: 'none', jobs: 'in-process' }`; `SssbApp`
already receives `params`. A deployment that does not use `SssbApp` sets the variables itself. Then delete the
placeholder values you set for the ports you switched off.

**Now deletable.** Placeholder values (`unused`, `unused-by-<app>`) set for `ANTHROPIC_API_KEY`, the Mailgun
variables, `EMAIL_FROM` or `JOBS_CODEBUILD_PROJECT` only so that real mode would start.

### Jobs and scheduled work without CodeBuild: the in-process runner and `SssbApp`'s scheduled tick

Action: optional · `@sssb/kit`, `@sssb/cdk`

**What changed.** `JOBS_RUNNER=in-process` (`params.ports.jobs: 'in-process'`) runs each job's registered handler in
the server, from the request or the scheduled tick that started it, records its terminal status and, for one of the app's own job kinds,
notifies its org's admins before that call returns: no CodeBuild project and no jobs webhook route. A job shares that invocation's time limit (30
seconds on `SssbApp`); longer work stays on `codebuild`. `SssbApp` takes a new option, `scheduledTick: { webhookSecret,
every? }`: an EventBridge rule (every five minutes unless `every` says otherwise) runs a function that reads that
secret and invokes the server directly with a POST of `/api/webhooks/cron`, the route behind `withWebhookSecret` that
`pnpm tick` calls in development. It goes through neither CloudFront nor the Function URL. Without the option nothing
changes in your stack.

**To adopt.** To run jobs without CodeBuild, set `jobs: 'in-process'` in `params.ports`. To run your scheduled work,
pass the secret your server's `WEBHOOK_SECRET` holds (a plain string secret):

```ts
new SssbApp(stack, 'Default', { ...props, scheduledTick: { webhookSecret } })
```

The construct grants its function read on that secret and invoke on the server; getting the value into the server's
`WEBHOOK_SECRET` stays yours. Close the `scheduled-tick` cutover row with its proof after the first deploy.

**Now deletable.** A ticker of your own (an EventBridge rule and a Lambda that POSTs a route of yours with the webhook
secret) whose route only does what a registered job kind and a `job_schedules` row would; and a route of your own that
runs scheduled work in the server because SSSB's real jobs port started every job as a CodeBuild build.

## Scaffold changes to apply by hand

### A generated app's proxy runs through `withAuthProxy`

Action: required · `@sssb/create`

**What changed.** The starter's `src/proxy.ts` wraps its locale routing in `withAuthProxy` from
`@sssb/kit/adapters/proxy`, and its matcher now also sends it every `/api` route (passed through untouched), so real

**To adopt.** Make your `src/proxy.ts` the one the kit changeset "Real-mode sign-in: `withAuthProxy` runs Clerk's

### The generated workspace installs without the eslint 10 peer warning

Action: optional · `@sssb/create`

**What changed.** The first `pnpm install` of a generated workspace printed "Issues with peer dependencies found", because `eslint-plugin-react` and `eslint-plugin-jsx-a11y`, which `@sssb/eslint-plugin`'s preset loads, declare eslint 9 as their highest peer while the preset and the workspace run eslint 10. No release of either lists eslint 10 yet. The generated `pnpm-workspace.yaml` now carries a `peerDependencyRules.allowedVersions` entry for exactly those two plugins, with a comment that says why and when to delete it.

**To adopt.** Nothing breaks if you do nothing; the warning is the only symptom. To silence it in an existing workspace, add this to `pnpm-workspace.yaml`, then delete it once `pnpm peers check` shows both plugins declare eslint 10:

```yaml
peerDependencyRules:
    allowedVersions:
        'eslint-plugin-react>eslint': '10'
        'eslint-plugin-jsx-a11y>eslint': '10'
```

**Now deletable.** Nothing.

### A generated app's port slot is its own, so it never says `starter`

Action: optional · `@sssb/create`, `@sssb/kit`, `@sssb/tools`

**What changed.** `pnpm create @sssb` now gives the app a port slot named for its slug, at port 3700:
`"sssb": { "port": { "name": "<slug>", "default": 3700 } }`, or `sssb-app` for a slug a slot cannot be named for. Its
override is `<SLUG>_PORT`. The app's `dev` and `tick` scripts (`sssb dev-tick`, `sssb tick`) and its
`playwright.config.ts` (`originForApp(__dirname)`) name no slot and read the declaration. Before, the app declared
SSSB's built-in `starter` slot (port 3100, `STARTER_PORT`) and named it in all three. The app guide's example now shows
a slot of the app's own. The generated README, `CLAUDE.md` and CI workflow name `pnpm exec sssb pin` where they say to
raise SSSB's pins. In `@sssb/tools`, `sssb tick`'s usage and `sssb port`'s refusal of an app with no declaration
lead with the app's own slot rather than SSSB's built-in ones.

**To adopt.** Nothing is required: `"sssb": { "port": "starter" }` keeps working, on the same port. To give your app a
slot of its own, as a new workspace's has:

```json
"sssb": { "port": { "name": "<your app>", "default": 3700 } }
```

in the app's `package.json` (any port from 1024 to 49151 outside SSSB's own: 3000, 3100, 3200-3599, 5439-5639,
20000-29999, 61000-61199). Then, in its scripts, `sssb dev-tick starter -- …` becomes `sssb dev-tick -- …` and
`sssb tick starter` becomes `sssb tick`; in `playwright.config.ts`, `originFor('starter')` becomes
`originForApp(__dirname)`, imported from `@sssb/tools/ports`. The app's local port then moves to the default you chose,
and its override from `STARTER_PORT` to `<YOUR_APP>_PORT`. A second app in the workspace must not take the same port.
Refresh the app guide's copy as after any upgrade (`pnpm exec sssb guide`).

**Now deletable.** A `starter` in an app's scripts and Playwright config, once the app declares a slot of its own.

### The root's Vitest configs read `sssb.apps`, and `sssb doctor` reports a knip config gap

Action: optional · `@sssb/tools`, `@sssb/create`

**What changed.** `@sssb/tools/vitest` exports `workspaceAppProjects({ root, options? })`: an `appTestProject` for each
app the root package.json's `sssb.apps` names (else every `apps/<name>`), in that order, with `options(appDir)` passed
to each. The two Vitest configs `@sssb/create` writes call it instead of keeping an `APPS` list, so `sssb.apps` is the
one list of a workspace's apps. `sssb doctor` reports (never fails) an app, or an app's seam package, that the root's
knip config (`knip.json`, `knip.jsonc`, `.knip.json` or `.knip.jsonc`) gives no workspace of its own, and a root
`@sssb/create` that knip would call unused.

**To adopt.** Optional: a workspace that keeps its `APPS` lists keeps working, and `sssb doctor` still fails a config
that stops running an app's conformance suite. To read `sssb.apps` instead, in `vitest.config.ts`:

```ts
import { workspaceAppProjects } from '@sssb/tools/vitest'

// in place of: projects: await Promise.all(APPS.map((app) => appTestProject({ appDir: at(`./apps/${app}`) })))
projects: await workspaceAppProjects({ root: at('.') }),
```

and in `vitest.contract.config.ts`, the same projects narrowed to the contract tests:

```ts
projects: (await workspaceAppProjects({ root: at('.') })).map((project) => ({
    ...project,
    test: { ...project.test, environment: 'node', include: ['tests/contract/**/*.test.ts'] },
})),
```

then delete the `APPS` constant from both. Options an app's project took (`env`, `alias`, `testTimeout`) go in
`options: (appDir) => ({ … })`.

**Now deletable.** An `APPS` list in a root Vitest config that repeats the apps `sssb.apps` already names.

### `sssb remove-items` takes the starter's Items slice out in one step

Action: optional · `@sssb/tools`, `@sssb/create`

**What changed.** The first thing every adopter does is take out the starter's example Items slice by hand, over about fifteen files. `pnpm exec sssb remove-items` does it: the card, the route, the query, the ability, the `items` catalog namespace, the dashboard's glue and the static demo's card, the specs that name it, and the paging proofs; the Simulator's e2e spec stays, so the app still has one for `sssb check-e2e`. The migrations are the one thing it will not guess at. A database records each migration it runs, and the migrator refuses to start when a recorded one is gone from the code, so without `--drop-migrations` the command leaves `1001_items`, `1002_items_keyset_index`, `ItemsTable` and the `items` RLS proofs registered; with it, they go too, and the app is left with `AppSubjectType = never`, an empty `appMigrations`, an empty proofs body and `AppTables = Record<never, never>`. `--dry-run` lists what it would do. It computes every edit first and refuses, naming each file and changing nothing, when one is not what the starter wrote. The starter's proxy test now uses `/projects` for its sample paths, so nothing is left to name Items. The generated README now points at it, and `@sssb/tools` ships the two diffs it applies (`src/remove-items/*.patch`).

**To adopt.** Nothing, if your app already removed Items. In a workspace you have just generated, run `pnpm exec sssb remove-items --dry-run --drop-migrations`, then without `--dry-run`, delete `apps/<app>/.data`, and number your first table `1001_<name>`. Where a database has already run the migrations, run it without `--drop-migrations`. An app that edited the Items files or has its own migrations after `1002` is refused by design: finish by hand from SSSB's `docs/adopting-reference.md`, "To remove the Items slice".

**Now deletable.** A hand sweep over the Items slice's files.

### The starter declares the optional ports it uses

Action: optional · `@sssb/create`

**What changed.** The starter's `config/params.ts` has a `ports` entry: `llm: 'none'`, `email: 'mailgun'`,
`inboundEmail: 'none'` and `jobs: 'in-process'`, since the starter makes no model call, has no inbound email route and
no jobs webhook route. A workspace generated from now on deploys without an Anthropic key, an inbound signing key or a
CodeBuild project.

**To adopt.** Copy the `ports` entry into your own `config/params.ts`, beside `database`, and set each port to what
your app uses (the entry "Real mode requires only the optional ports your app uses" lists the values).

### The starter's items list pages, as the app guide requires

Action: optional · `@sssb/create`

**What changed.** The starter's `GET /api/items` returned every row, which broke the guide's rule that a list that can grow pages through `@sssb/kit/db/keyset` and made the example an adopter copies the wrong one. It now answers one page: it parses `?cursor=` with `parseDbKeysetCursor` and answers 400 `{ "error": "invalid-cursor" }` when it is `invalid`, clamps `?limit=` on the server, and orders by the primitive's fixed `created_at`, `id`, newest first. The response gains `nextCursor`. The query moves to `src/domain/db/items.ts` (`listItems`), migration `1002_items_keyset_index` adds the index the walk needs, the items card shows "Show older items" while a next page exists, and `src/app-config/db/rls-proofs.ts` proves a cursor from another team or tenant cannot widen a page.

**To adopt.** Nothing breaks if you do nothing; a route that never reads a cursor still works. To page a list of your own, copy the pattern: the route in `src/app/api/items/route.ts`, the query in `src/domain/db/items.ts`, the index migration (a separate migration for a table that already exists, or the index in the create migration for a new one), and the proofs at the end of `src/app-config/db/rls-proofs.ts`. The card and the dashboard glue show the "load more" side.

**Now deletable.** A hand-rolled `LIMIT`/`OFFSET` or an unbounded `.execute()` behind a list route.

### A generated app has the Simulator on its own `pnpm dev`

Action: optional · `@sssb/create`

**What changed.** The starter mounts SSSB's Simulator server host with `src/app/api/simulator/[...path]/route.ts` and renders the panel from `src/app/[locale]/layout.tsx` in simulated mode, so a generated app's `pnpm dev` (and its simulated builds) has the People, Mail and Jobs tabs, the world clock included. Until now the panel was only in its static demo. A new e2e spec, `tests/e2e/simulator.spec.ts`, signs in through the panel and opens its tabs.

**To adopt.** Copy the route file and the `SimulatorChrome` component and its use from the starter's `src/app/[locale]/layout.tsx` (the kit changeset "The Simulator's People, Mail and Jobs tabs on an app's own `pnpm dev`" shows both), and the spec if you want the gate.

### The lint preset now requires typescript-eslint 8.73

Action: optional · `@sssb/eslint-plugin`

**What changed.** `@sssb/eslint-plugin` now depends on `typescript-eslint` `^8.73.0` (it was `^8.72.0`). 8.73.0 takes
`minimatch` 11.0.1 or later, the first release that fixes GHSA-g3hv-75wg-m249 (a denial of service through a crafted
glob; moderate, in your lint tooling only); 8.72 takes `minimatch` 10, which is affected. A workspace generated at 0.2.0
or earlier also lists `typescript-eslint` `^8.72.0` in its own root `devDependencies`, and that range is what keeps 8.72
and `minimatch` 10 in its lockfile.

**To adopt.** Raise the workspace root's `typescript-eslint` to `^8.73.0` (or run `pnpm update typescript-eslint -r`) in
the same change that upgrades `@sssb/eslint-plugin`, so the workspace holds one copy of it, at 8.73. A workspace
generated from this release on already has that range.

## Other changes

### SSSB's adoption guide is short, with a reference beside it

Action: none · `@sssb/create`, `@sssb/tools`, `@sssb/kit`

**What changed.** SSSB's `docs/adopting.md` is now a short guide in the order you act: generate, first boot, take out
the starter's content, a first entity, deploy and cut over, upgrade by release. Everything else it held is in
`docs/adopting-reference.md`. `sssb remove-items`, when it refuses, now points at the reference's "To remove the Items
slice" for the steps by hand. A new workspace's `README.md` links both, the guide's "Upgrading by release" for
the steps and the reference's "Upgrading, step by step" for why each is there.

### `sssb doctor` reports your own GitHub settings and plugin install

Action: none · `@sssb/tools`

**What changed.** `sssb doctor` now also reports, without ever failing or changing anything, the settings only you can
make. When `gh` is signed in: whether `sssb / all-checks` is a required check on your repository's default branch (a
ruleset or branch protection), whether private vulnerability reporting is on, and, for a private repository in an
organization, whether its Actions policy lets it call SSSB's reusable workflow. Locally: whether the Claude Code plugin
your `.claude/settings.json` enables is installed (`claude plugin install <plugin> --scope project`). It makes
read-only GitHub requests through `gh`; a `gh` that is missing, signed out or offline, or a setting your account may not
read, gives "not checked" and the reason. None of it runs when `CI` is set.

**To adopt.** Nothing to do. After you upgrade, a local `pnpm exec sssb doctor` prints up to four more lines (`github:`
and `claude plugin:`), each `ok`, or `report` with what to change: the report never changes the exit code. Run
`gh auth login` first if you want the GitHub lines; in CI doctor prints one line saying it skipped them.

### A deployment loads `pg` and PostHog only when it uses them

Action: none · `@sssb/kit`

**What changed.** The real ports load the `pg` driver only for the `pg` transport (`DATABASE_TRANSPORT=pg`, the default) and PostHog only when
`POSTHOG_KEY` is set, as the Data API transport and the optional ports already did; a Data API deployment no longer
loads `pg`. Nothing to set or change.

### `sssb add-app <slug>` writes a second app into your workspace

Action: none · `@sssb/tools`, `@sssb/create`

**What changed.** `pnpm exec sssb add-app <slug>` writes a new app under `apps/<slug>/` from SSSB's starter, renamed as
`pnpm create @sssb` renames your first app (its slug, session cookie, package names, seam package and display name,
`--name "<Name>"`), taking each `@sssb` package as your first app takes it, on a port slot of its own (named for the
slug, its default the first free one from 3700 up; `--slot <name>` and `--port <port>` choose them), with scripts and a
Playwright config that read that slot, and names it in the root's `sssb.apps`. It prints what is left to you: the
root's `dev`, `tick` and `start` scripts and the CI workflow's `synth`, which name one app on purpose. The starter comes
from the `@sssb/create` installed at the workspace root, which exports the code as `@sssb/create/add-app`; no SSSB
package depends on another, so the command says how to install it when it is missing.

**To adopt.** Nothing to do. For a second app: `pnpm add -D -w @sssb/create@<your @sssb version>`, then
`pnpm exec sssb add-app <slug>`, `pnpm install` and `pnpm exec sssb doctor`, which names anything the workspace still
needs (a Vitest config that keeps its own list of apps, the new app's `knip.json` entries, a root `@sssb/create` knip
would call unused: remove it once your apps are written). `pnpm jscpd` fails while the new app is still the starter;
make the apps your own, or ignore `apps/<slug>/src/**` in `.jscpd.json` until you have.

### `sssb pin` raises both of your pins to the release commit

Action: none · `@sssb/tools`

**What changed.** A new command, `pnpm exec sssb pin`, reads the release commit the installed `@sssb/kit` records
(`dist/release.json`) and writes it into your two pins on SSSB's repository: the reusable workflow's `uses:` line in
`.github/workflows/*.yml` and the `ref` of the plugin marketplace in `.claude/settings.json`. It prints each pin it
changed and the commit it replaced, changes nothing in a pin that is already current, and edits only that text, so the
formatting of both files is kept; a version in the `uses:` line's comment (`# @sssb/create 0.2.0`, `# v0.2.0`) moves
with it, and a comment of your own stays. It refuses, writing nothing, when there is no commit to read (SSSB's own
repository, or a kit packed by hand) or a file is not the shape it edits: no workflow calls SSSB's reusable workflow,
or `.claude/settings.json` is not JSON or declares no marketplace from SSSB's repository. A workspace with no
`.claude/settings.json` has the workflow pin raised alone. "Upgrading to this release" in the notes and `sssb doctor`'s
report of a pin that differs now name it.

**To adopt.** Nothing is required. At your next upgrade, after you install the new packages, run `pnpm exec sssb pin` in place of
editing the `uses:` line and the marketplace's `ref` by hand, read the diff of the two files, and commit it with the
package versions. Each person then runs `claude plugin marketplace update sssb` and
`claude plugin update sssb@sssb --scope project`, as before.

**Now deletable.** Nothing in your code. The two hand edits the release notes asked of you on every upgrade, and any
script of your own that copies the release commit into those two files.
