# Release notes: v0.6.1

6 changes, 0 requiring action. 1 change has no adopter-visible effect and is not listed.

## Upgrading to this release

Every release asks these of a workspace, whatever its entries say. Make them on a branch, in order, then read the
entries below.

**1. Move every `@sssb/*` package to 0.6.1, together.** In the root `package.json`, each
`apps/<app>/package.json` and `apps/<app>/infra/package.json`, and any package of your own that depends on one,
change each `@sssb/*` version, then install and commit the lockfile. First make any "Scaffold changes to apply by
hand" entry below that touches how packages install, or the install keeps the old release.

```json
{
    "@sssb/kit": "^0.6.1",
    "@sssb/tools": "^0.6.1",
    "@sssb/eslint-plugin": "^0.6.1",
    "@sssb/cdk": "^0.6.1"
}
```

```sh
pnpm install
```

**2. Refresh the app guide's copy,** the rules every agent in your repository follows. `sssb doctor` fails until the
copy is the installed kit's; read the diff of `.claude/sssb-guide.md`.

```sh
pnpm exec sssb guide
```

**3. Raise both pins to this release's commit.** The reusable workflow's `uses:` in
`.github/workflows/checks.yml` and the plugin marketplace's `ref` in `.claude/settings.json` are two pins on one commit
of SSSB's repository, and the installed `@sssb/kit` records it. This reads it there and writes both, printing each pin it
changed, and does nothing to one that is already current. It refuses, changing nothing, when the kit carries no release
stamp or a file is not the shape it edits:

```sh
pnpm exec sssb pin
```

If it refuses, make the two edits by hand: the `uses: safeinsights/sssb/.github/workflows/app-checks.yml@<commit>` line and the
marketplace's `ref`. The commit is the one `sssb doctor` names beside a pin that differs or, for a kit with no stamp, the one this prints: `git ls-remote https://github.com/safeinsights/sssb 'refs/tags/v0.6.1' 'refs/tags/v0.6.1^{}' | tail -n 1 | cut -f 1`. A pin takes the commit's SHA, never the tag `v0.6.1`, which can be moved.

Then each person updates their installed plugin and restarts Claude Code:

```sh
claude plugin marketplace update sssb
claude plugin update sssb@sssb --scope project
```

**4. Apply each entry below, then drop what it left unused.** Do each "To adopt" and delete what each "Now deletable"
describes, then run `pnpm knip`. A vendor SDK your app listed only for code you deleted (`@aws-sdk/client-s3` for a
copy of the kit's S3 storage adapter, say) is now flagged as unused, because the kit's adapter that replaces it
carries its own copy: remove it from the `package.json` that lists it, unless other code still imports it.

```sh
pnpm knip
```

**5. Check, then push.** Read every line `sssb doctor` reports, not just the last: it fails on versions out of step and
a stale guide copy, and only reports a pin that is not the release commit.

```sh
pnpm exec sssb doctor
pnpm verify
```

## Seam changes

### Under a fixed org source, grant your own people before denying on `restricted`

Action: optional · `@sssb/kit`

**What changed.** The guide and the adopter reference now say what a fixed org source means for an app's rules.
Everyone it signs in has the role `none` (or `restricted`), and both are restricted, so `restricted` is `true` for
everyone and cannot tell an app's own admins from anyone else. `none` stays restricted on purpose, so nothing opens
silently.

**To adopt.** If you use a fixed org source (`params.auth.orgSource: 'fixed'`), check every rule in `appAbilityRules`,
and every route or screen that reads `user.restricted`. Each must grant your own people from your own data before it
denies on `restricted`. A check that denies on `restricted` first locks everyone out, your own admins included.

- Key the grant on `actor.userId`, never on an email.
- If only the person at the keyboard should have it, also check `actor.credential?.kind === 'session'`: an API token or
  an inbound email reaches your rules with the same `userId`.
- Your rules see `none` in no org (`sameOrg` is false), so a grant scoped to the home org needs
  `defaultRole: 'restricted'`.

### A person the tenant guard refuses can see why

Action: optional · `@sssb/kit`

**What changed.** Under a single tenancy, a person whose identity-provider account names another tenant (or holds a
tenant claim that is not a slug) is refused.
Before, they saw the sign-in form again while still signed in to the provider, with nothing saying why.

- The auth port gains an optional `refusal()`, which answers `{ reason: 'other-tenant' }` for such a person, and null
  otherwise.
- A new framework screen, `AccountRefused` (`@sssb/kit/components/auth/account-refused`), says the account belongs
  to another site. It offers one sign-out button, and says first that signing out also signs the person out of other
  sites that share the sign-in. Nothing signs them out on its own.
- Its real-mode form, `RealAccountRefused` (`@sssb/kit/adapters/real/account-refused-form`), signs out through Clerk's
  client. Without that, the browser's short-lived session token would bring the same screen back.

**To adopt.** In your sign-in page, after the `getCurrentUser` redirect, check `await auth.refusal?.()`. When it
answers, show the screen instead of the sign-in form:

- in real mode, `RealAccountRefused`, loaded with `import()`;
- in simulated mode, a small client glue that renders `AccountRefused` and posts JSON to your sign-out route.

The starter's `src/app/[locale]/signin/page.tsx` and `refused-glue.tsx` show both.

## Operator actions

### The Migrator runs on the RDS Data API

Action: optional · `@sssb/kit`

**What changed.** On the Data API transport (`DATABASE_TRANSPORT=data-api`) the Migrator failed on its first
statement with `UnsupportedResultException: The result contains the unsupported data type "CHAR"`. That statement is
Kysely's introspection, which selects `pg_class.relkind`, a one-byte `"char"` the Data API cannot return. The Data API
dialect now gives Kysely an introspector that reads the same thing with `relkind` cast to text. The Data API emulator
that `pnpm test:contract` runs on now refuses a result with a `"char"` column, as the Data API does, and also a
`char(n)` column and arrays of either, which the Data API very likely refuses too (the same JDBC type, unconfirmed). So a
statement the contract run sends that returns one fails there instead of live. Nothing changes on the `pg` transport.

**To adopt.** If your Migrator failed this way on the Data API, upgrade `@sssb/kit`, redeploy, and invoke the Migrator
again; it migrates from where the database stands. On the Data API transport, cast a `"char"` or `char(n)` column you
select to text (`code::text`). The contract run checks only the statements it sends (the migrations and the isolation
proofs), not every query your app makes.

### The Migrator Lambda loads

Action: optional · `@sssb/cdk`

**What changed.** `SssbApp`'s Migrator crashed as it loaded, before migrating anything, with `Dynamic require of
"events" is not supported`, on both network shapes: esbuild's ESM bundle of the handler inlines `pg`, whose CommonJS
`require` of Node's own modules has nothing to call in an ES module. The bundle now starts by defining `require` with
Node's `createRequire`. Every Node.js function `SssbApp` builds (the Migrator, the body-hash Lambda@Edge, the scheduled
tick) is now loaded in Node by SSSB's tests, so a bundle that cannot load fails CI.

**To adopt.** If your first migrate on 0.6.0 failed this way, upgrade `@sssb/cdk`, run `cdk deploy` (which rebuilds the
Migrator's bundle), and invoke the Migrator again; it migrates from where the database stands, which is empty. Nothing
else changes, and a stack that has not deployed yet only needs the upgrade.

**Now deletable.** A `bundling.banner`, or a `format` override, added to the Migrator through an escape hatch to make it
load.

## Scaffold changes to apply by hand

### The starter's sign-in page tells a refused person why, and its sign-out takes JSON only

Action: optional · `@sssb/create`

**What changed.**

- `src/app/[locale]/signin/page.tsx` asks the auth port whether the signed-in person is refused. If they are, it shows
  the refused-account screen instead of the sign-in form: `RealAccountRefused` in real mode, and a new
  `refused-glue.tsx` in simulated mode.
- `src/app/api/auth/signout/route.ts` now refuses a request that is not JSON (`refuseNonJson`, 415). A page on a sibling
  subdomain, which the browser sends the session cookie with, could otherwise sign a person out with no click. The
  header's sign-out and the new glue send `content-type: application/json`.
- `page.test.tsx` and `route.test.ts` pin both.

**To adopt.** Copy the sign-in page's refusal branch if you run a single tenancy. Copy the sign-out route's
`refuseNonJson` check, and the JSON header on every caller of that route, whatever your settings.
